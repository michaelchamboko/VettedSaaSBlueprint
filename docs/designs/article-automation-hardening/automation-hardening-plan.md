## 2. Design choice

Retain existing stages, format validators, editorial procedures, leases, atomic writers, release adapters, and owner verifiers. Add versioned contracts and a shared pure evidence evaluator; stage handlers still own transitions. The registry describes applicability and dispatches existing checks, rather than becoming another workflow engine.

A separate verification service would improve separation of authority but adds credentials, deployment and operation beyond the selected local-evidence scope. Independent terminal-only checks would be smaller but allow packet, intake, and release rules to diverge. Shared evaluation plus stage-specific mutations closes those bypasses without a new service, scheduler, model client, or lifecycle stage.

Success means all supported mutation paths reject incomplete chains before side effects; read-only inspection diagnoses historical inconsistencies without changing them; tests demonstrate both valid passage and rejection, including concurrency and crash recovery. A clean scanner alone is never editorial, semantic, design, or production proof.

Add strict Zod contracts in src/lib/article-import/workflow-evidence.ts. Use existing stable artifact fingerprint helpers for artifact identity; raw file references additionally bind SHA-256 bytes. Every reference is `{path, sha256}` with repository/state-root containment, symlink escape rejection, regular-file check and bounded read. New records use ExternalArticleImportV2 (existing core fields plus workflowVersion:2, requirementRevision, evidenceRefs, diagnosis history and terminalRef). Add explicit future CLI `--upgrade-evidence <import-id>`: primary checkout, import lease, archive original bytes, validate source identity, preserve counters/history/old receipts as untrusted legacy, create V2 at earliest unsatisfied stage with no fabricated approval. It never resumes work or changes intake status. Legacy reads remain supported; legacy mutating commands return LEGACY_UPGRADE_REQUIRED until explicit upgrade. Unknown versions return UNSUPPORTED_VERSION. No bulk migration occurs in this task.

Proposed strict companion schemas (all have schemaVersion literal, id, createdAt, importId, sourceFingerprint, requirementRevision):

* WorkflowEvidenceV1: stage, packetId, artifactRef when applicable, predecessorRefs, ruleResults[]. Each rule result has ruleId/revision, status pass/fail/not-applicable/recommendation-not-adopted, scoped rationale, evidenceRefs. No pass with unresolved required findings.
* ResearchEvidenceV2: sources[{id,url,retrievedAt,snapshotRef}], claims[{id,text,sourceIds,excerptLocations,limitations}], freshness assessment; producer is supervising research action, validator checks structure, bindings and scoped judgment, not remote truth by hash.
* ContentAssessmentV1: format, artifactFingerprint/schemaRevision, intent{audience,decision,query,pageType}, claimCoverage, SEO/AEO ruleResults, reviewerExecutionRef, findings[{id,artifactPaths,claimIds,description,disposition,evidenceRefs}]. Unresolved required finding blocks approval.
* EditorialExecutionV1: editorialEvidenceRef, schemaRevision, eligibleProsePaths, passes[{name,inputRef,outputRef,instructionRefs,executionRef,judgmentRef}], checkerExecutionRef. Names/order are three SlopMonster passes, cleanse, fidelity. Each input equals predecessor output; complete eligible prose projection checked each pass; fidelity explicitly approves meaning/protected fields and claims. Existing EditorialEvidenceV2 remains required and unchanged in meaning.
* ExecutionEvidenceV1: producer kind command/browser/opencode, tool version, inputRefs, outputRefs, startedAt/completedAt, exit/status, and discriminated producer payload. Commands retain executable/argv/cwd/stdout/stderr/exit code; browser retains target/routes, viewport, observed checks and screenshot refs; OpenCode uses the adapter below. No secrets/private reasoning in retained output.
* TerminalEvidenceV1: kind live/quarantine/duplicate; originImportId, immutable sourceRef, requirementRevision, completion time; live adds frozen approved artifact/evidence chain, reviewed commit, deployment identity, productionVerifierRef; quarantine adds reason code and dispositionEvidenceRef; duplicate adds verified originTerminalRef, never copied origin receipts attributed to new identity.
* DiagnosisV1: stage, failedSubmissionDigest, failureCode, cause, attemptedRecoveryRefs, remedyEvidenceRefs, replacementSubmissionDigest, createdAt, consumedAt optional. Diagnosis cannot approve gates or change stage.

Keep content approval and presentation version dispatch explicit: ImportContentApprovalV2 references content assessment/editorial companion, existing approval identity and requirement revision; ImportPresentationV2 references actual executions/judgments and frozen artifact/routes. ImportReleaseV2 retains actual production verifier reference. V1 records can be inspected but cannot satisfy V2 transitions. Remove fallback parsing that hides invalid evidence, retaining diagnostic paths in compatibility decoding.

State evidence lives under ignored `.automation/article-imports/evidence/<import-id>/<sha256>.*`, created exclusively and never overwritten. Source bytes retained there before disposable normalized input deletion. Reviewable content/editorial artifacts remain under build-pack/editorial and existing canonical artifact paths. Frozen historical bundles snapshot exact bytes, not mutable path-only references. Post-review deployment/terminal evidence remains ignored state, so it does not change the reviewed Git head. Tests inject isolated state roots; public CLI offers no bypass switch.

## 7. Shared evaluator, transitions, concurrency and recovery

Introduce `evaluateWorkflowEvidence(record, context, mode)` returning `{ok, diagnostics, earliestRequiredStage, validatedRefs}`. Modes are historical-terminal, current-transition, duplicate-reuse. Reads have no writes, leases, process launches or network requests. Reuse validators in content-approval.ts, presentation.ts, verification-evidence.ts and format-validation.ts. Call evaluator from executePendingImport, advanceImport, verifyImportRelease, completion, createArticleImport duplicate resolution, and intake reconciliation.

| State/action | Required predicate and outcome |
|---|---|
| Normal stage submission | Current stage packet/result identity, byte-bound dependencies and applicable gates; only then advance one stage and append source-stage/destination-stage receipt |
| LIVE completion inspection | Historical frozen live bundle validates at its recorded requirement version/commit; later edits to current files do not invalidate history; missing legacy proof reports unverified terminal, never silently COMPLETE |
| QUARANTINED inspection | Source identity, documented allowed unusable-input reason and genuine disposition evidence; no demand for later research/editorial/release; missing work or model access cannot become quarantine |
| Duplicate source | Preserve new reference identity and immutable source; verify original historical completion plus current applicable reuse requirements; if not reusable return work/repair with origin link, never clone old receipt identities into a new completed record |
| Intake LIVE/QUARANTINED update | Reload referenced import and prove matching source and terminal predicate; arbitrary patch/status flag rejected |
| Article-specific demonstrated obstacle | Durable blocker records cause, attempted recovery, exact resumption condition; may advance snapshot, never counted published |
| Shared capability/access/integrity/release failure | Stop folder, preserve PROCESSING identity; no next article |
| Missing packet, approval or editorial work | WORK/REPAIR on same entry, not durable blocker and not skip |
| Explicit retry of resolved blocker | Existing intake-retry operation clears only that blocker under lock; preserves snapshot, order, history and counters |

Historical evaluator dispatches retained known requirement versions, not the newest policy. New transitions and duplicate reuse use current policy. Invalid historical receipts remain visible without editing existing public pages. `--check-completion`, `--check-intake`, `--describe-workflow`, `--preflight` are read-only diagnostics. Preserve existing CLI completion exit-code mapping (0/10/20/30) with additional structured error codes, rather than treating failed proof as success.

Use an intake-run lease and import lease with immutable exclusive-create claim files, owner tokens and existing generation semantics. Validate lease ownership before each atomic write. Intake mutators take runId/entryId and expected revision, never a caller-owned whole snapshot. Inside the short intake critical section reload, select/reconcile earliest PROCESSING, validate proof, update revision and atomically persist. Release it before long work. Work executes under the import lease; final reconciliation reacquires intake lease and reloads. Do not hold both leases simultaneously. Cross-snapshot reuse is serialized by import identity and lease. Incomplete claim files are treated as busy/corrupt, never free. Expiry marks an abandoned-work suspicion only; it never permits automatic takeover. Every new claim binds machine identity, PID, process-start identity and owner token. All protected state writes must execute in that owning process. Add explicit future --recover-lease <kind> --key <id-or-fingerprint> (kind source/intake/import), which never executes imports: positively verify that the previous local process identity has exited, then use exclusive next-generation claiming so competing recoveries select one successor. A live owner, remote machine, unknown or partial identity, unavailable process-status probe, or unverifiable legacy claim stays stopped with LEASE_RECOVERY_UNVERIFIED. PID alone is insufficient because of PID reuse; a reused PID is distinguishable only by verified process-start identity. This is fail-closed liveness loss rather than permission to delete a claim. Keep ownership checks before writes, but do not treat those checks as atomic fencing. Test expiry, partial files and simultaneous claimants.

Before allocating an import ID, both direct-source and intake creation must acquire an exclusive source claim keyed by the immutable source fingerprint. Under that claim reload `.automation/article-imports/source-index/<fingerprint>.json`; reuse its reserved import ID, or atomically reserve exactly one new ID before writing its import record. Reservation stores sourceRef, sourceFingerprint, importId and creation time. If a crash leaves a reservation without a record, the next source-claim holder completes creation at that same ID from validated retained source bytes; missing or mismatched bytes stop with SOURCE_RESERVATION_INVALID, never allocate a replacement ID. Legacy identity conflicts produce SOURCE_IDENTITY_CONFLICT for explicit repair, not arbitrary selection. The source claim uses the same no-time-only-takeover policy, explicit dead-owner recovery, exclusive generation and owner checks as other leases. Never hold source, intake or import leases together: intake selection persists source identity first, source reservation follows after releasing intake lease, attach the reserved ID under a new intake lease, then execute under import lease. Repeating any phase uses the existing reservation. This closes the race before an import-ID lease can exist.

If import commits terminal before intake update, next read reports discrepancy; explicit intake-resume reconciles terminal proof before selecting next entry. If intake selected PROCESSING but import execution crashed, next resume uses the same source/import; it never creates another active claim. No inspection repairs state. Operation keys and revision comparison make repeat updates idempotent.

Add explicit `--upgrade-intake <run-id>`: under intake lease archive exact V1 bytes once, verify captured source identities, add V2 revision/version and preserve every original status/order/import reference. Repeating it validates and returns the existing V2 record without another migration. It performs no import upgrade, execution or status reconciliation. Before selecting any pending entry on an explicit intake-resume, inspect all terminal-labeled entries for proof discrepancies. If a LIVE/QUARANTINED label lacks valid proof, including LIVE pointing to an upgraded nonterminal import, stop the whole run with INTAKE_TERMINAL_PROOF_INVALID, identifying the earliest affected entry; do not silently skip or continue. Add explicit `--reconcile-intake-entry <run-id> --entry <relative-path>`: require a matching source/import identity, upgraded V2 records and a nonterminal import with an earliest unsatisfied stage; under intake lease preserve original status in history, mark that entry PROCESSING, and preserve order/counters. It neither resumes the import nor publishes. If another PROCESSING entry exists, stop with INTAKE_RECONCILIATION_CONFLICT rather than creating a second active entry. Unsupported or conflicting proof requires explicit repair and remains stopped. Only a later explicit intake-resume can execute the repaired entry. These future migration commands are not run in this task.

Repair digest includes canonical stage/packet/result fields plus bytes of every referenced artifact/evidence/dependency; exclude timestamps/attempt counters. Same path with changed bytes is a different submission. Unchanged failing input yields UNCHANGED_SUBMISSION and no retry. Retain existing detailed counters/history and add cumulative unsuccessful-repair counts keyed by importId plus productive stage, aggregated across strategies, changed inputs and changing error messages. Derive initial counts from retained history during explicit upgrade; incomplete history stops with REPAIR_HISTORY_INCOMPLETE rather than assuming zero. At three failed repairs for that import/stage require DiagnosisV1 with observed cause and verified remedy; `--submit-diagnosis <id> --file <path>` only registers that diagnosis under import lease. It neither executes work nor resets counters. The next explicit resume consumes it once only when failed digest/stage and replacement digest match; another failure requires a new diagnosis once threshold has been reached. Stale/consumed/wrong-stage diagnosis rejects. Ordinary successful progression clears active repair state while preserving history and stage totals.

Invalidation: source changes require a new immutable source/import identity. Any artifact content/schema/protected-field/structure change invalidates final editorial reuse, assessment, approval, presentation and release eligibility. Presentation-only CSS/render changes with identical artifact bytes retain content/editorial approval but invalidate affected presentation and release checks. Instruction/requirement revisions invalidate current transition dependencies they own; they never rewrite historical completion. Existing strict editorial fingerprint rules are not weakened by a prose-only shortcut.
