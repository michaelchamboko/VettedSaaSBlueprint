# UI Catalogue Council Review — 2026-08-30

## Question and context

QUESTION: Should the user’s delegated approval add five modern, popular, engaging visual references to each of eight landing-page categories?

CONTEXT: The library stores implementation-ready pattern metadata, not third-party code. The user requires 2026 currency and a verifiable popularity signal; any unverified claim remains out.

## Stage 1 — Independent answers

- **A:** Approve only candidates that pass the evidence gate; a pattern library is useful when retrieval is predictable, not merely large.
- **B:** Approve a deliberately varied set—editorial, grid, carousel, accordion, comparison, and motion—so later pages gain compositional freedom.
- **C:** Approve conditionally: explicit 2026 publication and a public popularity signal are required; unknown licence rights cannot be upgraded to permission.
- **D:** Approve only with durable metadata for date, popularity type, and reuse caution, otherwise the library becomes an unreliable prompt dump.
- **E:** Approve reference patterns, not copied designs; transparent provenance protects both users and original creators.

## Stage 2 — Blind review

### A reviews

1. **C** — C is strongest because it makes the claim boundary testable, though it does not specify how diversity is preserved.
2. **D** — D is second because durable metadata prevents future drift, though it depends on C for factual admission criteria.
3. **B** — B usefully protects compositional variety, though it risks accepting novelty without a hard evidence gate.
4. **E** — E correctly protects creators, though it lacks an operational selection rule.

### B reviews

1. **D** — D is strongest because a broad library fails without retrieval-quality metadata, though it underweights visual variety.
2. **C** — C protects accuracy, though its threshold alone cannot prevent a visually monotonous collection.
3. **A** — A gives a clean acceptance rule, though it says too little about how patterns should differ.
4. **E** — E is ethically necessary, though it needs a concrete workflow to affect selection.

### C reviews

1. **D** — D is strongest because it makes evidence auditable after the initial decision, though it relies on C to reject weak claims.
2. **A** — A is rigorous about the central mechanism, though it does not explicitly record evidence type.
3. **E** — E sets the necessary reuse boundary, though it does not test recency or popularity.
4. **B** — B improves the outcome only after the evidence gate has already passed.

### D reviews

1. **C** — C is strongest because it prevents unverified metadata from entering the system, though it needs D to remain durable.
2. **A** — A gives a usable first-principles filter, though it does not model downstream retrieval.
3. **B** — B keeps the library useful for composition, though it cannot validate a candidate alone.
4. **E** — E protects legitimacy, though it needs structured record fields to scale.

### E reviews

1. **C** — C is strongest because it avoids making rights or popularity claims beyond the evidence, though it needs a durable record to remain visible.
2. **D** — D faithfully preserves obligations for later implementers, though it does not decide which candidates deserve entry.
3. **B** — B avoids a sterile library, though engagement must remain subordinate to truthfulness.
4. **A** — A is efficient, though it needs E’s human-duty boundary to remain legitimate.

## Stage 3 — Debate

1. **Popularity evidence**
   - **C:** Individual download claims must be public and reproducible; otherwise the candidate fails.
   - **D:** Source-library adoption can be retained only if its level is explicit in each record, so a later user cannot mistake it for per-component demand.
   - **B:** A strictly individual-download threshold would discard useful contemporary patterns where the platform exposes only featured status or library adoption.
   - **Test:** Component copy counts were not publicly reproducible, while direct 21st page-level featured metadata and source-library data were.
   - **Winner:** Evidence-labeled conditional approval; featured status is component-level and source-library adoption stays expressly source-level.

2. **Engagement versus novelty**
   - **B:** The set needs varied visual and interaction patterns to support later composition.
   - **A:** Motion that does not clarify hierarchy, state, or product character adds cost without increasing utility.
   - **D:** Tags and layout notes let the system select the interaction level intentionally, including a still fallback.
   - **Test:** The approved set covers grids, carousels, accordions, tables, motion, and static alternatives across the eight categories.
   - **Winner:** Varied, purposeful interaction; motion is not an approval criterion by itself.

3. **Reuse rights**
   - **E:** A public page does not grant permission to copy its implementation or proprietary imagery.
   - **C:** A licence cannot be inferred from visibility, a generic repository, or a source-level association.
   - **D:** The catalogue must make the implementation-time licence and accessibility review an explicit next step.
   - **Test:** Some component pages exposed licence text while others did not, so a uniform reuse claim would be false.
   - **Winner:** Visual-reference-only records with component-specific licence review before any source adoption.

## Stage 4 — Chair's verdict

**Recommendation:** Approve the 40 listed references as a constrained visual-pattern batch. Store their recency and popularity evidence with every record and treat all source code and licences as separate implementation decisions.

**Reasoning that survived:** Direct 2026 publication evidence prevents stale selection; featured/source-library evidence makes popularity transparent; layout and tag diversity supports later composition.

**Council disagreement:** Source-library adoption is weaker than individual download data, but individual data was not publicly reproducible. It is accepted only where labeled as source-level.

**Strongest argument against:** A 40-record batch can create choice overload. Mitigation: tags, categories, and the Council gate limit retrieval; gpt-taste remains free to produce bespoke UI when a reference is not the best fit.

**First three actions:** 1. Add and verify the 40 records. 2. Use tags and layout notes to retrieve candidates during page builds. 3. Verify implementation rights and accessibility/reduced-motion behavior before adopting any source code.
